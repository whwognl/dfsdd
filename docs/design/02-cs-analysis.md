# 02. CS 사례 분석 — 실제 기록 기반 CS 탭 확장 설계

작성일: 2026-09-06
근거 자료
- 사용자 워크북 `CS` 시트(총 928행, 조치내용이 적힌 실제 사례 91건) → `cs_cases.json`
- 같은 시트 1행의 "CS 메뉴얼", BM열 "CS 멘트" 텍스트, 셀 드롭다운(데이터 유효성) 정의
- 구앱 `app.js`의 `CS_TYPES` / `CS_STATUSES` / `csCost` / `memoLog` / `renderCsPane` / 출고중지·반품접수 체크 흐름 / `invoiceExcluded`

표기 규칙
- "확인" = 데이터·코드를 직접 읽어 확인한 사실. "추정" = 텍스트 정황에서 유추한 것.
- 이 문서에는 고객명·연락처·계좌·주문번호·송장번호·구매처 계정 별칭을 **한 건도 옮기지 않았습니다.** 패턴만 적습니다.

## 0. 한눈에 보는 결론

1. 91건 중 **반품(구매처 반품 신청 → 회수 → 환불)** 이 43%, **등급차액 협의(고객에게 소액 입금)** 가 29%로 두 유형이 CS의 72%를 차지합니다. 8월 사례의 86%(78/91)가 쌀 한 상품에서 발생했습니다(확인).
2. 사람이 실제로 기다리는 대상은 4가지뿐입니다: **고객 회신**, **구매처 처리**, **택배 회수**, **쿠팡(확인요청/환불)**. "누구를 기다리는 중인가"가 곧 진행 상태입니다.
3. 자유 텍스트 안에 늘 같은 것이 반복됩니다: 날짜 접두(`8/6`), 부호 있는 금액(`(-6000)`, `(+12000)`), 회수 송장(택배사 + 12자리), `입금 필요`→`입금 완료`, `회수 안됨 → 재회수`, `환불 완료 끝`, 강조(`!!!!!!`, `*****`). 이것들이 그대로 구조화 필드 후보입니다.
4. 시트의 `구분`(53% 공란), `진행상태`(75% 공란), `방식`(77% 공란)은 사실상 안 쓰이고, `세부단계`(95% 채움)의 "컨텍 필요 / 조치완료" 두 값만 실제 신호로 쓰입니다. 즉 사용자가 원하는 건 **"지금 내가 해야 할 일이 남았나"** 하나입니다.
5. 제안: 구앱의 `csType / csStatus / csCost / memoLog`를 **그대로 두고 필드를 덧붙이는** 방식으로 확장합니다. 유형 7종 + "누구를 기다리나" + 단계 체크리스트 + 부호 있는 금액 장부 + 회수 송장 + 다음 조치일. CS 탭은 "오늘 할 일 / 기다리는 중 / 종결" 3단 구조.

## 1. 실제로 발생하는 CS 유형과 빈도

91건의 조치내용을 읽고 첫 번째 원인 키워드로 분류했습니다(확인, 규칙 기반 1차 분류 + 눈으로 보정).

| 유형 (제안 코드) | 건수 | 비율 | 텍스트에서 보이는 전형 문구 |
|---|---:|---:|---|
| 반품 — 구매처 반품 신청 후 회수 (`return`) | 39 | 43% | "구매처 반품 신청 완료 (-6000)", "회수 완료", "환불 완료 끝" |
| 등급/차액 협의 — 고객에게 소액 입금 (`partial_refund`) | 26 | 29% | "등급차액 3000원 제시", "입금 필요", "8/23 입금 완료", "괜찮다 하심 종결" |
| 출고 전 취소 / 출고중지 (`cancel_before_ship`) | 6 | 7% | "출고중지요청 / 취소 완", "배송 출발로 무료반품 접수" |
| 택배 미수령 (`not_received`) | 5 | 5% | "미수령 신고 완", "미수령 반품 신청 완료 (0)", "파손 반송으로 인한 미수령" |
| 단순변심 반품 — 고객이 배송비 부담 (`return` + 양수 금액) | 3 | 3% | "변심 반품 (+12000) / 구매처 반품 신청 완료 / 환불 완료" |
| 품절 취소 (`soldout_cancel`) | 2 | 2% | "품절 취소 필요 → 품절 취소 완료" |
| 과배송 (`over_shipped`) | 1 | 1% | "과배송 / 구매처 회수 요청함 / 받음" |
| 배송지연 반품 (`return`, 사유=배송지연) | 1 | 1% | "배송지연 반품 / 무상반품 신청 완료 회수안내 필요" |
| 회수만 남은 건·미분류 (`other`) | 8 | 9% | "잘못시킴 회수 필요", "문자 요청 / 확인 필요" |

시트 드롭다운에 정의된 `구분` 값(확인): `배송 문의, 택배 미수령, 출고 전 취소, 반품, 교환, 추가 발송, 처리 논의중`.
- `교환`, `추가 발송`은 실제 기록에 0건입니다(교환 요청이 1회 문장에 등장하나 결국 차액 입금으로 끝남).
- `처리 논의중`은 유형이 아니라 상태입니다(실제 사용 6건 모두 차액 협상 중이었음).
- `배송 문의` 1건은 내용상 등급차액 입금이었습니다 → 유형 오기입.

시트 드롭다운의 `세부단계`(확인): `컨텍 필요, 1차 컨텍, 2차 컨텍, 마무리 단계, 연락 안받음, 조치완료, 안내필요, 로스, 쿠팡확인요청`.
실사용은 `조치완료` 57, `컨텍 필요` 24, `안내필요` 3, `쿠팡확인요청` 2. 나머지 5개 값은 0건.

시트 드롭다운의 `방식`(확인): `전화, 문자, 판매자센터, 주문누락, 실수` — 접수 채널과 원인이 한 목록에 섞여 있고, 실사용은 `판매자센터` 16, `문자` 5뿐.

### 유형별 부가 관찰 (확인)
- **반품의 금액 패턴**: 구매처 반품비로 `(-6000)` 15회, `(-10000)` 13회. 같은 상품인데 8월 하순부터 -10000으로 바뀜(추정: 구매처 또는 반품 정책 변경). 즉 "반품비"는 상품/구매처마다 다르고 시기에 따라 바뀌므로 **기본값은 있되 건별로 수정 가능**해야 합니다.
- **차액 협의 금액**: 2000·3000·4000·5000원, 3000원이 최빈(11회). 고객이 거절하면 반품으로 전환되고, "괜찮다"고 하면 종결.
- **쿠팡 측이 먼저 끝나는 반품**: "쿠팡 반품 완료 / 구매처 반품 필요" 7건. 고객 환불은 쿠팡이 이미 처리했고 **셀러가 구매처에 반품하는 일이 남은** 상태. 이때 구매처 반품 기간(7일)이 지나 "반품 불가 → 다른 계정/주문으로 반품 신청" 하는 우회가 13건 문장에 등장(구매처 계정 별칭 + 새 주문번호 + "31,940원 환불 예정"). 추정: 새 주문번호로 반품 접수를 다시 잡는 방식. 이 경우 **"구매처 반품 접수 주문번호"가 원주문과 달라지므로** 별도 필드가 필요합니다.
- **회수 실패**: "회수 안됨 / 재회수 신청" 10건(반품 39건 중 약 1/4). 원인 중 하나는 안심번호(0502)라 택배사가 고객에게 연락 못 함 → 고객 실번호 요청 멘트가 매뉴얼에 있음(확인).
- **보관 기한**: "9월 N일까지 상품 보관" 3건. 추정: 구매처/택배 회수 전까지 고객 또는 쿠팡 측 보관 기한. 날짜형 마감 필드가 필요한 근거.
- **강조 메모**: `!!!!!!!`, `*****` 8건 — 전부 "아침에 문자 드리기 꼭", "재회수 신청할 것" 같은 **다음 행동 리마인더**입니다. 앱에서는 `nextActionAt` + 오늘 할 일 목록이 이 역할을 대신해야 합니다.
- **연월 오류**: `일자` 열은 91건 중 88건이 같은 날짜(채우기로 복사된 값, 확인)이고 문장 안 날짜(`8/6`~`8/31`, `2026. 8. 10`)와 맞지 않습니다. 실제 발생일은 텍스트 접두에만 있습니다. → 앱은 **메모마다 자동 타임스탬프**(구앱 memoLog가 이미 함)를 유지하고, CS 발생일은 첫 메모 시각으로 잡으면 됩니다.

## 2. 유형별 처리 단계(상태 머신)와 "누구를 기다리나"

기록에서 반복되는 순서를 그대로 옮겼습니다. 각 단계 오른쪽은 그 단계에서 **사람이 기다리는 대상**입니다.

### 2-1. 반품 `return` (39건 + 변심 3건 + 배송지연 1건)
```
[접수] 고객 반품 요청 / 쿠팡 반품 접수 확인
  → [안내] 고객에게 절차 안내(문자/판매자센터)              기다림: 없음(내 차례)
  → [구매처 반품 신청] 반품비 확정 (-6000 / -10000 …)        기다림: 구매처
  → [회수 송장] 택배사 + 송장번호 확보, Wing 반송장 등록      기다림: 구매처(송장 발급)
  → [회수 대기]                                            기다림: 택배(회수)
       ↳ 회수 안됨 → [재회수 신청] → 회수 대기 (반복)          기다림: 고객(실번호) or 택배
  → [회수 완료]
  → [환불 확인] 구매처 환불 입금 확인                        기다림: 구매처
  → [종결] "환불 완료 끝"
분기: 구매처 반품 기간 초과 → 다른 주문/계정으로 반품 재접수(대체 주문번호·환불예정액 기록)
분기: 회수 최종 실패 → 쿠팡확인요청(매뉴얼 Case-1/2) 기다림: 쿠팡
```
변심 반품은 같은 흐름에 **고객 부담 배송비(+12000)** 가 수입으로 들어옵니다.

### 2-2. 등급/차액 협의 `partial_refund` (26건)
```
[접수] 고객 불만(등급 차이·개봉 후 사용 등)
  → [제시] 금액 제안(문자)                                  기다림: 고객(수락/계좌 회신)
       ↳ 수락 → [입금 필요] 계좌 확보                       기다림: 없음(내 차례: 이체)
                → [입금 완료] → [종결]
       ↳ "괜찮다" → [종결]
       ↳ 거절 → 반품 흐름(2-1)으로 전환
```
금액은 항상 **셀러 지출(-)** 로 마진에서 빠집니다.

### 2-3. 출고 전 취소 `cancel_before_ship` (6건)
```
[접수] 고객 취소 요청 → [출고중지] 쿠팡 출고중지 처리
  → [구매처 취소 요청]                                      기다림: 구매처
       ↳ 취소 성공 → [종결] (비용 0)
       ↳ 이미 배송 출발 → 무료반품/회수 접수 → 반품 흐름(2-1)
```
구앱의 `출고중지요청` 체크가 정확히 이 첫 단계입니다(확인). 송장 업로드 제외(`invoiceExcluded`)도 유지.

### 2-4. 택배 미수령 `not_received` (5건)
```
[접수] 고객 미수령 신고 → [쿠팡 미수령 신고/반품 처리]        기다림: 쿠팡
  → [구매처 반품 신청 (0원)] 또는 [구매처와 소통 후 취소]     기다림: 구매처
  → [환불 확인] → [종결]
```
1건은 "파손 반송으로 인한 미수령"(택배가 파손 판정으로 반송) — 사유 태그 `damaged`.

### 2-5. 품절 취소 `soldout_cancel` (2건)
```
[구매처 품절 확인] → [쿠팡 취소·환불] → [고객 안내(품절 멘트)] → [종결]
```

### 2-6. 과배송 `over_shipped` (1건)
```
[확인] → [구매처에 회수 요청]  기다림: 구매처/택배 → [회수 완료] → [종결]
```

### 정리: "기다리는 대상" enum은 5개면 충분
`me`(내가 할 차례) · `customer`(고객 회신) · `supplier`(구매처) · `courier`(택배 회수) · `coupang`(쿠팡 확인요청·환불).
시트의 `컨텍 필요`(24건)는 대부분 `customer` 또는 `me`, `쿠팡확인요청`은 `coupang`에 대응합니다.

## 3. 자유 텍스트 안에서 반복되는, 구조화 가능한 데이터

| 패턴 | 출현(90건 중) | 예시 형태(개인정보 제외) | 앱 필드 제안 |
|---|---:|---|---|
| 날짜 접두 | 84 | `8/6 …`, `05.26 …`, `2026. 8. 10` | memoLog `at` 자동 기록(이미 있음) |
| 부호 있는 금액 | 34 | `(-6000)`, `(-10000)`, `(+12000)`, `(0)` | `csLedger[]` 부호 있는 금액 항목 |
| 입금 필요 / 입금 완료 | 13 / 18 | "3000원 입금 필요 → 8/23 입금 완료" | ledger 항목의 `settled` 플래그 + 단계 체크 |
| 고객 계좌 | 6 | "은행명 + 계좌번호 + 예금주"가 조치내용에 그대로 적혀 있음 | **저장 지양**. 입금 직후 지우거나, 저장하더라도 내보내기·백업에서 제외 |
| 회수 송장 | 13 | `CJ 8446…`(12자리), `한진 5738…`(12자리), `롯데 2581…`(12자리) | `pickup.courier`, `pickup.trackingNo` |
| 회수 안됨/재회수 | 10 | "회수 안됨, 재회수 신청할 것" | `pickup.attempts`(횟수) + 단계 되돌리기 |
| 회수 완료 / 환불 완료 / 끝 | 6 / 14 / 14 | "회수 완료", "환불 완료 끝" | 단계 체크 → `csStatus=처리완료` 자동 |
| 구매처 대체 주문 | 13 | "계정 별칭 + 새 주문번호 + (31,940원 환불 예정)" | `supplierClaim.orderNo`, `supplierClaim.account`, `supplierClaim.expectedRefund` |
| 환불 예정액 | 8 | "(31940원 환불 예정)", "42570원으로 반품 신청" | `supplierClaim.expectedRefund` |
| 보관 기한 | 3 | "9월 21일까지 상품 보관" | `deadline`(날짜) |
| 강조 리마인더 | 8 | "아침에 문자 드리기 꼭 !!!!!!!", "재회수 신청할 것 *****" | `nextActionAt` + `nextAction`(한 줄) |
| 쿠팡 측 선처리 | 7 | "쿠팡 반품 완료 / 구매처 반품 필요" | 단계 체크리스트에 "쿠팡 환불 완료" 항목 |
| 반품 기간 초과 | 2 | "7일 지나서 반품 불가" | 사유 태그 `window_expired` + 대체 주문 필드 |
| 상품 사용/개봉 | 4 | "이미 사용함 / 뜯음 / 개봉된 상태" | 사유 태그 `opened` (차액 협의로 유도되는 근거) |
| 접수 채널 | 21 | 판매자센터 / 문자 (전화·통화 문장도 있음) | `channel`: `phone / sms / seller_center / etc` |
| 수량 2개 | 2 | "2개", "33110*2" | 주문 수량 그대로 사용(이미 있음) |

한 건의 조치내용은 평균 4.3개 조각(`/` 또는 줄바꿈 구분)으로 이루어져 있습니다(확인). 즉 사용자는 이미 "타임라인"으로 적고 있고, 구앱의 `memoLog`(항목마다 시각)가 그 습관과 정확히 맞습니다.

## 4. 현재 CS 시트/구앱의 비효율

### 4-1. 워크북 CS 시트 (확인)
- **CS 행 = 주문 행 복사본**: L~BK열(12~63열)에 `2.주문서` 행이 통째로 붙어 있고 거기에 계정·카드·수수료 계산까지 딸려 옵니다. 주문 한 건이 CS가 되면 시트 두 곳에 같은 데이터가 생기고, 계정/카드 정보가 CS 시트에도 번지는 구조입니다. → 구앱처럼 **주문 객체에 CS 필드를 얹는 방식이 옳고**, 사용자 습관과도 일치합니다.
- **분류 열이 비어 있음**: 내용이 있는 91건 기준 `구분` 47%, `진행상태` 25%, `방식` 23%만 채움. 드롭다운 값이 9개까지 되니 고르기를 포기하고 조치내용에만 씁니다.
- **`진행상태`와 `세부단계`의 역할 중복**: `진행상태`(진행중/조치완료)와 `세부단계`(조치완료 포함)가 같은 뜻을 두 번 묻습니다. 실사용은 세부단계 하나.
- **종결 표시가 텍스트("끝")에만 있음**: `세부단계=조치완료`인데 마지막 문장이 "재회수 필요"인 건이 4건, `진행중`인데 "환불 완료 끝"인 건이 1건 → 상태 미갱신.
- **`일자` 열 신뢰 불가**: 88/91건이 동일 날짜(채우기 복사). 발생일은 텍스트 접두에만 존재.
- **금액이 마진에 연결되지 않음**: `(-6000)` 같은 손실이 텍스트 안에 있어 DAY/MON 집계에 자동 반영되지 않습니다.
- **개인정보가 자유 텍스트에 섞임**: 고객 계좌(은행·번호·예금주)가 조치내용에 그대로 적힘. 입금이 끝난 뒤에도 남아 있습니다.
- **리마인더를 기호로 대신함**: `!!!!!!!`, `*****`가 "내일 아침 할 일" 표시. 정렬·필터가 안 됩니다.

### 4-2. 구앱 CS 탭 (`renderCsPane`, 확인)
- `CS_TYPES` 7값 중 실제 진입 경로는 체크박스 2개(`출고중지요청`, `반품접수`)뿐. 위 분석의 최다 유형 **등급/차액 협의(29%)**, **택배 미수령**, **품절 취소** 진입 버튼이 없습니다.
- `CS_STATUSES`(접수/처리중/처리완료/보류)는 "누구를 기다리나"를 표현하지 못합니다. 실제 필요한 건 `고객 회신 대기`, `구매처 대기`, `회수 대기`, `내 차례`.
- `csCost`는 **양수 하나**만 있어 `(+12000)` 같은 회수 수입, 여러 번 나뉜 지출(반품비 + 차액 입금)을 못 담습니다.
- 회수 송장, 구매처 반품 접수 주문번호, 환불 예정액, 다음 조치일 필드가 없어 전부 memo에 넣어야 합니다 → 시트와 똑같은 문제로 돌아갑니다.
- CS 목록은 반품 우선 + 주문일순 단일 정렬. "오늘 내가 처리할 것"이 위로 오지 않습니다.
- `csStatus` select 변경 시 전체 재렌더로 포커스가 날아갑니다(인수인계 문서에도 기록됨).
- 좋은 점(유지): CS 주문은 주문관리 시트에서 빠져 CS 탭에 모임, `csCost`가 순마진에서 차감, 출고중지·반품·취소 주문은 송장 업로드에서 자동 제외, 메모에 자동 시각, 시트에도 메모가 보임.

## 5. 제안 — 구앱 CS 구조를 **확장**하는 설계

원칙: `csType`, `csStatus`, `csCost`, `memoLog`는 이름과 의미를 유지합니다. 새 필드는 전부 선택적이며 `normalizeOrder()`에서 기본값을 채워 기존 저장 데이터가 그대로 열리게 합니다. `computeMargin()`의 `- toNumber(o.csCost)`는 그대로 두고, `csCost`를 장부 합계에서 **파생**시키기만 합니다.

### 5-1. 데이터 모델 (주문 객체에 추가)

```js
// 기존 (유지)
csType:   "",          // 아래 CS_TYPES 값. "" = CS 아님
csStatus: "",          // 기존 4값 유지 + 파생 규칙 (아래)
csCost:   0,           // = csLedger 합계(지출 − 수입). 장부가 비면 기존처럼 직접 입력값 사용
memoLog:  [{ at, text }],

// 추가
cs: {
  openedAt:   "2026-08-06 10:12",   // 첫 CS 체크 시각 (자동)
  closedAt:   "",                   // 종결 시각 (자동)
  reason:     "",                   // 사유 태그: change_of_mind | grade_diff | damaged | opened | delivery_delay | not_received | soldout | window_expired | wrong_order | etc
  channel:    "",                   // 접수 채널: phone | sms | seller_center | etc
  waitingOn:  "me",                 // me | customer | supplier | courier | coupang
  steps:      { "notify": true, "supplier_claim": true, "pickup_tracking": false, ... }, // 유형별 체크리스트 (아래 5-3)
  nextAction: "",                   // 한 줄: "아침에 문자", "재회수 신청"
  nextActionAt: "2026-08-28",       // 날짜. 오늘 이하이면 '오늘 할 일'로 올라옴
  deadline:   "",                   // 보관/반품 기한 (선택)
  pickup: { courier: "", trackingNo: "", attempts: 0, doneAt: "" },   // 회수 송장
  supplierClaim: { orderNo: "", account: "", expectedRefund: null, refundedAt: "" }, // 구매처 반품/취소 접수 (대체 주문 포함)
  coupangRequest: { filedAt: "", note: "" },   // 쿠팡확인요청
  ledger: [ { at, kind, amount, settled, note } ] // 부호 있는 금액 장부 (아래)
}
```

**CS_TYPES 확장** (기존 값은 그대로 남겨 호환, 새 값 추가):
```js
var CS_TYPES = ["", "출고중지요청", "반품접수", "차액협의", "택배미수령", "품절취소", "과배송", "교환문의", "배송문의", "취소요청", "기타CS"];
```
- 진입 체크박스/버튼은 `출고중지`, `반품`, `차액협의`, `미수령` 4개면 기록의 93%를 덮습니다. 나머지는 CS 탭 안의 유형 칩에서 변경.
- `invoiceExcluded()`에 `택배미수령`은 넣지 않습니다(이미 발송된 건). `품절취소`는 넣습니다.

**csStatus 파생 규칙** (사용자가 직접 고르지 않아도 됨):
- 단계 체크리스트의 마지막 항목이 체크되면 `처리완료` + `closedAt`.
- `waitingOn === "me"` 이거나 `nextActionAt <= 오늘` → `접수`/`처리중` 중 처리중.
- 그 외 대기 중 → `처리중`. `보류`는 사용자가 수동으로.

**ledger.kind (enum)와 부호**
| kind | 부호 | 기록 예시 |
|---|---|---|
| `supplier_return_fee` 구매처 반품비 | − | (-6000), (-10000) |
| `customer_compensation` 고객 차액 입금 | − | 3000원 입금 |
| `customer_paid_shipping` 고객 부담 배송비 | + | (+12000) |
| `reship_cost` 재발송·추가 배송비 | − | (기록엔 없으나 드롭다운의 '추가 발송' 대비) |
| `coupang_settlement` 쿠팡 추가정산(회수 실패 보상) | + | 매뉴얼 Case-2 |
| `etc` | ± | |

`csCost = Σ(−amount)` 즉 지출 합 − 수입 합. 장부 항목마다 `settled`(입금/정산 완료) 체크가 있어 "입금 필요 → 입금 완료" 흐름을 그대로 담습니다. **고객 계좌번호는 필드로 두지 않습니다**(입금은 은행 앱에서 하고, 앱에는 "입금 완료"만 남김). 정 필요하면 `note`에 잠시 적되 `settled` 체크 시 자동으로 비우는 옵션을 권장합니다.

**memoLog 확장**: `{ at, text, kind }` 에 `kind`를 추가(`note | step | money | contact`). 단계 체크·장부 추가·회수 송장 입력 시 자동으로 한 줄씩 memoLog에 남겨 **타임라인 = 메모**가 되게 합니다. 기존 항목은 `kind` 없음 = `note`.

### 5-2. 화면 구조 (CS 탭)

```
CS관리   [전체 12] [내 차례 4] [고객대기 3] [구매처대기 2] [회수대기 2] [종결 27]   CS차감 −124,000
──────────────────────────────────────────────────────────────
▌오늘 할 일  (waitingOn=me 또는 nextActionAt≤오늘 — 위로)
  [반품] 상품명 · 옵션 · 결제액        다음: 재회수 신청  8/28   [+메모] [복사▾] [주문으로]
  [차액] 상품명 …                       다음: 3,000원 입금  ● 입금 필요
▌기다리는 중  (대상별 정렬, 3일 이상 지나면 회색→주황)
  [반품] … 회수 대기 · CJ 8446… · 2회차   구매처 환불예정 31,940
▌종결 (접기, 기본 닫힘 · 이번 달 합계만 표시)
```

한 행을 펼치면(아코디언, 전체 재렌더 없이 해당 행만 갱신):
1. **유형 칩** 한 줄: 출고중지 · 반품 · 차액협의 · 미수령 · 품절취소 · 과배송 · 기타 — 클릭으로 변경. 유형에 따라 사유 태그 칩(변심/등급차이/파손/개봉/배송지연/기간초과/오주문).
2. **단계 체크리스트**(5-3) — 체크하면 `waitingOn`이 자동 이동하고 memoLog에 한 줄 기록.
3. **금액 장부**: `[+ 반품비 −6,000] [+ 차액 입금 −3,000] [+ 고객배송비 +12,000]` 빠른 버튼 + 금액 수정 + `입금/정산 완료` 체크. 합계가 순마진에 즉시 반영(대시보드·로스관리·월별 집계 그대로).
4. **회수 송장**: 택배사 select(설정의 배송사 코드 목록 재사용: CJ/한진/롯데/로젠/천일/업직) + 번호 + `회수 안됨` 버튼(attempts+1, 단계 되돌림, 다음 조치 "재회수 신청" 자동 제안).
5. **구매처 접수**: 접수 주문번호 · 계정(설정의 계정 별칭 목록에서 선택, **내보내기 제외**) · 환불 예정액 · 환불 확인 체크.
6. **다음 조치**: 한 줄 텍스트 + 날짜(기본: 오늘/내일/3일 후 버튼). `!!!!!` 대신 여기에.
7. **메모 타임라인**: memoLog 최신순, 자동 기록(step/money)은 옅은 글씨, 사람이 쓴 메모는 본문 색. 기존 `openMemo` 모달도 그대로 동작.
8. **복사 버튼**: 이름 · 전화 · 주소 각각 1회 클릭 + "한 번에" (기존 `copyAutofill`은 자동입력용이라 전화가 '내 번호'로 들어감. CS의 **회수 접수용 복사는 고객 실번호가 필요**하므로 "회수용 복사(고객 번호)"를 별도 버튼으로 두고 라벨에 명시. 자동입력 정책과 충돌하지 않게 함수 분리).
9. **멘트 버튼**: 유형에 맞는 템플릿(5-5)을 골라 상품명·금액만 치환해 클립보드로.

### 5-3. 유형별 단계 체크리스트 (steps 키)

| 유형 | 단계 키 (순서) | 체크 시 waitingOn |
|---|---|---|
| 반품 `반품접수` | notify(고객 안내) → coupang_return(쿠팡 반품 접수 확인) → supplier_claim(구매처 반품 신청·반품비) → pickup_tracking(회수 송장·Wing 등록) → picked_up(회수 완료) → refunded(구매처 환불 확인) → closed | me → supplier → supplier → courier → supplier → me → 종결 |
| 차액협의 `차액협의` | proposed(금액 제시) → accepted(수락·계좌 회신) → paid(입금 완료) → closed | customer → me → 종결. `declined` 버튼 = 반품으로 전환 |
| 출고중지 `출고중지요청` | stopped(쿠팡 출고중지) → supplier_cancel(구매처 취소 요청) → cancelled(취소 확인) → closed | supplier → me. `already_shipped` 버튼 = 반품으로 전환(무료반품) |
| 택배미수령 | reported(미수령 신고) → coupang_handled(쿠팡 처리) → supplier_claim(구매처 반품/취소 0원) → refunded → closed | coupang → supplier → me |
| 품절취소 | confirmed(품절 확인) → cancelled(쿠팡 취소환불) → notified(고객 안내) → closed | me |
| 과배송 | supplier_pickup(구매처 회수 요청) → picked_up → closed | courier → me |
| 기타 | notify → resolved → closed | 사용자가 waitingOn 직접 선택 |

공통 분기 버튼: `쿠팡확인요청 접수`(waitingOn=coupang, coupangRequest.filedAt 기록), `회수 안됨`(attempts+1).

### 5-4. 주문관리 ↔ CS 이동

- 주문관리 시트의 `출고중지` / `반품접수` 체크박스는 유지. 그 옆에 **`CS ▾` 드롭 버튼** 하나를 추가해 `차액협의`, `택배미수령`, `품절취소`, `과배송`, `기타`를 한 번에 고르게 합니다(열 추가 없이 메모 셀 옆 미니 버튼). 고르면 `csType` 세팅 + `cs.openedAt` + 첫 memo 자동 + CS 탭으로 즉시 이동(현재 `toast`만 띄우는 것을 "이동" 버튼 포함 토스트로).
- CS 행의 **`주문으로`** 버튼: 주문관리 탭을 열고 해당 행을 하이라이트·스크롤(검색어에 주문번호를 넣는 방식이면 코드 변경 최소).
- 대시보드의 "CS/반품 n건" KPI 카드와 로스관리의 CS 행에도 같은 `주문으로`/`CS로` 링크를 붙여 **어디서든 한 번에** 이동.
- CS 해제(기존 `clearCsOrder`)는 유지하되, 장부에 금액이 있으면 "차감액 −6,000이 남아 있습니다. 해제하면 마진에서 빠지지 않습니다" 확인 창.
- 종결된 CS 주문은 주문관리 시트로 **돌아가지 않고** CS 탭 "종결" 섹션에 남되, 시트 필터 "CS 포함" 토글로 볼 수 있게(현재 `sheetFiltered()`가 CS를 무조건 숨기므로 토글 하나 추가).

### 5-5. 자주 쓰는 CS 멘트 템플릿 (원본 매뉴얼·멘트 열에서 유형만 추출, 개인정보·계좌 제외)

원본 1행 "CS 메뉴얼"과 BM열 "CS 멘트"에 실제 존재하는 문안의 **유형**입니다(확인). 문안 본문은 사용자가 설정에서 편집하고, `{상품명}`, `{금액}`, `{입금계좌}` 자리표시자만 치환합니다.

| 키 | 언제 | 원본에 있는 문안의 요지 |
|---|---|---|
| `soldout_cancel` | 품절 취소 후 | 공급사 품절로 배송 불가, 취소·환불 처리했다는 사과 |
| `ack_generic` | 접수 직후 1차 응답 | 불편 사과, 담당 부서 확인 후 조치하겠다는 안내 |
| `need_real_phone` | 회수 접수 전(안심번호일 때) | 회수 접수에 010 실번호가 필요하니 회신 요청 |
| `shipped_notice` | 출고 안내 | `{상품명}` 출고되었다는 안내 |
| `cancel_too_late` | 출고 후 취소 요청 | 이미 배송 시작으로 취소 불가, 수령 후 반품 가능·왕복배송비 부과, 정상 수령 원하면 앱에서 취소철회 안내 |
| `refunded_pay_back` | 쿠팡 환불 완료 후 고객이 정상 수령한 경우 | 이미 환불된 건이니 정상 수령 시 `{입금계좌}`로 이체 후 입금자명 회신 요청 |
| `partial_refund_offer` | 차액 협의 | (원본에 완성 문안 없음 — 기록상 "n천원 안내 문자"가 11회 이상이므로 **사용자에게 문안을 받아** 등록 권장) |
| `pickup_notice` | 회수 송장 등록 후 | (원본 없음, "회수 안내 필요" 8회 → 문안 추가 권장) |

`{입금계좌}`는 **설정 > 내 입금계좌**에서만 치환하며, 이 값은 어떤 내보내기·백업 파일에도 포함하지 않습니다(기존 계정/카드 원칙과 동일). 멘트 텍스트에 고객 정보는 넣지 않습니다.

매뉴얼의 쿠팡 회수 지원 절차(Wing > 주문/배송 > 반품 관리 > 입고 송장번호 > 운송장등록, 회수 실패 시 이관글·쿠팡확인요청, 고객 사유 최종 회수 실패 시 상품가 100% 추가정산)는 CS 행의 `쿠팡확인요청` 단계 옆 도움말 툴팁으로 넣으면 됩니다.

### 5-6. 대시보드·집계 연결 (기존 코드 재사용)
- `csCost`가 장부 합계로 바뀌어도 `computeMargin`, 월별 `csCost` 집계, 로스관리 목록은 수정 없이 동작합니다.
- 대시보드 KPI에 `CS 진행 n건 (내 차례 m건)` 하나만 추가하고 클릭 시 CS 탭 "오늘 할 일"로.
- 월별 표에 `반품 n건 · 차액협의 n건` 유형별 건수(`csType` 그룹)를 붙이면 8월처럼 한 상품에 CS가 몰리는 상황이 바로 보입니다.

### 5-7. 마이그레이션 메모
- 기존 저장 데이터: `cs` 객체 없음 → `normalizeOrder`에서 빈 기본값 생성, `csCost`는 기존 값 그대로 유지(장부가 비어 있으면 장부 합계로 덮어쓰지 않음).
- 워크북 CS 시트를 가져올 때는 **주문 행에 매칭해 `csType`·memoLog로만** 넣고(조치내용 → 메모 1건, 날짜 접두는 그대로 텍스트), 시트 구조를 탭으로 옮기지 않습니다. 조치내용 안의 금액 `(-6000)` 패턴은 장부 항목으로 자동 변환 가능하나, 계좌번호 패턴은 가져오기에서 **마스킹**해야 합니다.

## 6. 위험·주의
- 사례의 86%가 8월 한 상품(쌀)에서 나온 것이라 유형 비율은 이 달의 특수성을 반영합니다. 패션 상품 중심 달에는 변심 반품·교환 비중이 오를 수 있습니다(추정). 그래서 유형 enum에 `교환문의`를 남겨 두었습니다.
- 반품비 기본값(-6000/-10000)은 시기·구매처에 따라 달라졌으므로 하드코딩하지 말고 설정값 + 건별 수정으로.
- 회수 접수용 "고객 번호 복사"는 자동입력용 `copyAutofill`(내 번호 고정)과 반드시 별개 함수로 두고 라벨을 분명히 해야 기존 정책이 흐트러지지 않습니다.
- 고객 계좌는 저장하지 않는 쪽을 기본으로. 저장하더라도 `exportFull` 등 모든 내보내기에서 `cs.ledger[].note`를 제외하거나 마스킹.
